# ADR: v0.5 Formula-Derived Variables

**Status**: ACCEPTED 2026-07-07 — Phase A (algebraic formulas), via a `mockFormula` extension column on `variable_details`, evaluated as a post-baseline stage in a restricted sandbox. Any individual decision remains open to maintainer revision before implementation begins.
**Date**: 2026-07-07
**Decision owner**: MockData maintainers
**Issue**: #39
**Depends on**: #38 (seed contract — reserves the `formula` sub-stream index)

## Decision summary

| D2 | Evaluation model | **(a)** Post-baseline stage over generated data — **no new seeded-output break** (#39 rides #38's) |

Key property of D2(a): because formula variables depend on generated *values*
(which exist regardless of generation order), the evaluator needs no whole-spec
reorder — random variables keep their draw order, so #39 adds no seeded-output
break beyond #38's. It co-releases with #38 in v0.5 but does not spend a second
break.

## Context

Derived variables are the reason the recodeflow ecosystem exists: cchsflow and
chmsflow are, in large part, libraries of variables *derived* from raw survey
items (BMI from height/weight, risk scores from many inputs). MockData today
**detects and skips** them — `identify_derived_vars()` (`R/identify_derived_vars.R`)
finds `DerivedVar::` (in `recStart`) and `Func::` (in `recEnd`) patterns and
excludes those variables from generation, leaving derivation to the downstream
pipeline. So mock data cannot exercise the derivation logic it exists to test:
a user testing a cchsflow recode gets mock raw inputs but no mock derived
outputs, and must derive them by hand.

The v0.4 spike (merged in PR #27, later removed from the tree, recoverable at
`git show f4f9b41:development/v04-simstudy-spike/prototype.R`) already prototyped
the hard parts:

- `formula_dependencies(var)` — extracts referents via `all.vars(str2lang(var$formula))`.
- `order_spec_by_dependencies(spec)` — topological sort with cycle detection
  ("Formula dependency cycle or unresolved ordering among: …").
- `validate_formula_referents(spec)` — errors on formulas referencing unknown
  variables.
- Evaluation: `eval(str2expression(var$formula), envir = data, enclos = parent.frame())`.

Two spike details are load-bearing for this ADR. First, the spike **reorders the
whole spec** by dependency before generating — which would change the order in
which *random* variables consume the RNG stream, shifting seeded output. Second,
its eval uses `enclos = parent.frame()` — which is **not a sandbox**: a formula
could reach any binding up the call stack. Both must be reconsidered here.

The `mock_spec` variable constructor already carries unused `formula` and
`depends_on` fields (`R/mock_spec.R:101,106`), reserved for exactly this.

### Constraints

- **Downstream semantics.** cchsflow/chmsflow (CRAN) consume `DerivedVar::`/`Func::`
  from the same metadata. MockData must not *redefine* what those mean. A
  MockData-extension column is the safe channel (same rule as the seed and
  garbage extensions).
- **Seed contract (#38).** The seed ADR reserves a `formula` sub-stream (index 2).
  How formula evaluation relates to baseline generation determines whether #39
  adds a *second* seeded-output break or rides #38's single break — a decision
  below, not an assumption.
- **Dependency ethos.** Evaluation must stay in base R (`eval`/`str2lang`); no new
  dependency. Any function dispatch (Phase B) must not force the consuming
  package to be attached for the native path to work.
- **Scope boundary.** MockData generates *plausible test data*, not validated
  synthetic data. A derived variable computed from mock inputs is only as
  meaningful as those inputs — this is a testing aid, restated in docs.

## Decision points

Recommendations given, not enacted. No code until accepted.

### D1 — How does a formula enter the metadata?

- **(a) New MockData-extension column `mockFormula`** on `variable_details` (or
  `variables`). A variable with a non-empty `mockFormula` is generated by
  evaluating that expression over already-generated columns. `DerivedVar::`/`Func::`
  keep their current recodeflow meaning untouched.
- **(b) Reuse `DerivedVar::`/`Func::`.** Infer the formula from the existing
  recodeflow notation.

**Recommendation: (a).** Reusing (b) would make MockData reinterpret recodeflow's
derived-variable notation as an executable generation formula — a semantic change
to a schema two CRAN packages depend on. A dedicated `mockFormula` column is
additive, self-documenting, ignored by other recodeflow tools, and lets a
variable be *both* a real `DerivedVar::` downstream *and* mock-generated here.
See D6 for how this flips a variable from "excluded" to "generated".

### D2 — Evaluation model: post-baseline stage, or whole-spec reorder?

- **(a) Post-baseline stage.** Generate all random (non-formula) variables first,
  in their existing order, then evaluate formula variables as a distinct stage
  over the assembled data frame — using #38's reserved `formula` sub-stream for
  any randomness *inside* a formula. Formula variables are topologically ordered
  *among themselves* (a formula may reference another formula's output).
- **(b) Whole-spec topological reorder** (the spike's approach): order every
  variable by dependency and generate in that order.

**Recommendation: (a).** It has a decisive property: **it adds no new
seeded-output break.** Random variables keep their generation order, so their
draws are unchanged; formula columns are appended deterministically (or draw from
the isolated `formula` sub-stream if a formula includes noise). #39 therefore
*rides* #38's single v0.5 break rather than adding a second one. (b) would
reshuffle random draws and force another break, for no functional gain —
formulas depend on generated values, which exist regardless of generation order.
Cycle detection and referent validation from the spike carry over, scoped to the
formula set.

### D3 — Evaluation sandbox

The spike's `enclos = parent.frame()` is unsafe. For a testing tool run on the
user's own machine the threat model is modest (accidental reference to a stray
global, a typo resolving to some function), not adversarial — but the evaluator
should still be *predictable and self-contained*.

- **Environment:** evaluate in an environment whose only variables are the
  generated columns, with `enclos` set to a **restricted parent** exposing an
  explicit allow-list of base operators/functions, not `parent.frame()` and not
  the global environment.
- **Allow-list (to ratify/amend):** arithmetic and comparison operators
  `+ - * / ^ %% %/% ( )  < <= > >= == != & | !`; `ifelse`, `pmin`, `pmax`, `min`,
  `max`, `abs`, `round`, `floor`, `ceiling`, `sqrt`, `exp`, `log`, `log10`,
  `sum`, `mean`, `cut`, `as.numeric`, `as.integer`, `as.factor`, `factor`. A
  formula referencing anything outside the generated columns + this list errors
  at validation time (extend `validate_formula_referents()` to check function
  symbols, not just variable referents).
- **No** filesystem, network, `system`, `eval`/`parse` re-entry, or `<<-`.

**Recommendation:** restricted-parent environment + ratified allow-list, validated
up front so a bad formula fails with a clear message before any generation.

### D4 — Scope of #39: Phase A only, or A + B?

- **Phase A — algebraic formulas** over generated columns (`mockFormula =
  "weight / (height^2)"`). Fully covered by the spike's eval; bounded by the D3
  sandbox.
- **Phase B — `Func::` dispatch** to a derivation function in the consuming
  package's namespace: generate the raw inputs, then *call the real derivation
  function* on them. Powerful (exercises actual cchsflow logic) but raises the
  hardest questions: namespace lookup order, what happens when the package isn't
  loaded, and it steps outside the D3 allow-list by design.

**Recommendation: Phase A in #39; Phase B as a separate future workstream (own
issue, own ADR).** Phase A delivers the core value (mock derived variables for
pipeline tests) at low risk and no new dependency. Phase B's coupling and
sandbox questions deserve their own decision and shouldn't hold up the v0.5
co-release with #38. Note the deferral in `NEWS`/docs so users know `Func::`
generation is not yet supported (those variables stay excluded — D6).

### D5 — Diagnostics

Formula variables should be distinguishable in the `mockdata_diagnostics`
attribute: a per-variable entry marking `derived = TRUE` (or a `source =
"formula"` field) plus the resolved dependency list. This lets downstream checks
tell generated-from-formula columns from directly-sampled ones.

**Recommendation:** add `derived`/`formula`/`depends_on` to each formula
variable's diagnostics entry, consistent with the existing diagnostics shape.

### D6 — Interaction with `identify_derived_vars()`

Today every `DerivedVar::`/`Func::` variable is excluded from generation. Under
D1(a):

- A variable with a non-empty `mockFormula` is **generated** by the evaluator —
  it moves from "excluded" to "generated", even if it also carries `DerivedVar::`
  (its downstream derivation notation is untouched).
- A derived variable **without** `mockFormula` stays **excluded** exactly as today
  (external derivation), including all `Func::` variables until Phase B exists.

**Recommendation:** ratify this rule — `mockFormula` is the explicit opt-in for
"MockData, generate this derived variable yourself." Backward compatible:
metadata with no `mockFormula` behaves identically to today.

## Guarantee / scope statement (to ratify)

> A variable with a `mockFormula` is generated by evaluating that expression, in
> dependency order among formula variables, over the generated data, in a
> restricted environment exposing only the generated columns and a fixed
> allow-list of base functions. Formula evaluation is deterministic given its
> inputs; any randomness inside a formula draws from the isolated `formula`
> sub-stream (#38) and does not perturb baseline variables. A derived value is
> only as meaningful as the mock inputs it is computed from — this is a testing
> aid, not validated synthetic data.

## Consequences

**If accepted as recommended (D1a, D2a, D3 restricted, D4 Phase A, D5, D6):**

- Recover the spike's `formula_dependencies` / cycle-detection / referent
  validation into `R/` (scoped to the formula set), add the restricted-env
  evaluator, and run it as a post-baseline stage keyed to #38's `formula`
  sub-stream.
- Add the `mockFormula` extension column to the recodeflow adapter and the
  direct API (populate the existing `formula`/`depends_on` spec fields).
- **No new seeded-output break** beyond #38's — #39 rides the v0.5 break.
- `identify_derived_vars()` gains a `mockFormula`-aware carve-out (generate vs
  exclude).
- `Func::` generation remains unsupported (documented), pending Phase B.

**Costs / risks:**

- The sandbox allow-list is a maintained surface; too narrow frustrates users,
  too wide erodes the "predictable/self-contained" property. Start narrow (D3),
  widen on concrete request.
- Formula validation must run *before* generation so errors are early and clear
  (referent + function-symbol checks), not a mid-generation `eval` failure.

## Test strategy

New `tests/testthat/test-formula-vars.R`:
1. Algebraic derivation correctness (e.g. BMI = weight / height^2 matches a
   hand computation over the generated columns).
2. Formula-of-a-formula (dependency ordering among formula variables).
3. Cycle detection errors clearly; unknown-referent errors clearly; a
   disallowed function symbol errors at validation, before generation.
4. Seed behaviour: a deterministic formula adds no change to baseline variables'
   seeded output (pin a baseline variable's values with and without a formula
   variable present); a noisy formula is reproducible via the `formula`
   sub-stream and does not perturb baseline.
5. Diagnostics: formula variables marked derived with their dependency list.
6. `identify_derived_vars()` carve-out: `mockFormula` → generated; bare
   `DerivedVar::`/`Func::` → still excluded.
